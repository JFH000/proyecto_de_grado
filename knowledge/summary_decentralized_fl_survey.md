# Summary: "Decentralized Federated Learning: Fundamentals, State of the Art, Frameworks, Trends, and Challenges"

**arXiv:** [2211.08413](https://arxiv.org/abs/2211.08413)
**Authors:** Enrique Tomás Martínez Beltrán, Mario Quiles Pérez, Pedro Miguel Sánchez Sánchez, Sergio López Bernal, Gérôme Bovet, Manuel Gil Pérez, Gregorio Martínez Pérez, Alberto Huertas Celdrán (University of Murcia / University of Zürich / Armasuisse)
**Type:** Survey (IEEE Communications Surveys & Tutorials), first literature review specifically on Decentralized FL (DFL) as opposed to Centralized FL (CFL)
**Companion framework:** Fedstellar (by the same lead author), https://github.com/enriquetomasmb/fedstellar

## What the paper covers

The paper is organized around four research questions and follows a "fundamentals → frameworks → application scenarios → trends/challenges" storyline:

1. **Q1 — Fundamentals/taxonomy of DFL**, the core section for this thesis's purposes, split into:
   - **Federation architecture**: federation type (cross-silo: <100 nodes, large data, e.g. hospitals/orgs; cross-device: >100 nodes, small data, e.g. edge/IoT/robots), participant role (trainer, aggregator, proxy, idle), **decentralization schema** (DFL vs. Semi-Decentralized FL/SDFL vs. CFL — see below), and data distribution (IID/non-IID, horizontal/vertical/transfer FL).
   - **Network topology**: fully connected, partially connected (star, ring, random/Erdős–Rényi), and node clustering (similarity-based or proxy-based hierarchical clusters).
   - **Communication mechanisms**: synchronous/asynchronous/semi-synchronous schemes, plus the two decentralized communication paradigms, **peer-to-peer (P2P)** and **gossip**.
   - **Security and privacy**: malware/Byzantine/Sybil/Eclipse/free-rider attacks specific to serverless settings, and countermeasures (DP, SMC/HE, TEEs, blockchain/DLT).
   - **KPIs** (node, communication, model) and **optimization mechanisms** for each.
2. **Q2 — Frameworks**: compares mature CFL-rooted frameworks (TFF, PySyft, FederatedScope, FedML, LEAF) against incipient DFL-native ones (BrainTorrent, Scatterbrained, IPLS, TrustFed, FLoBC, BLADE-FL, DISCO, CMFL, DisPFL, GossipFL, and **Fedstellar**).
3. **Q3 — Application scenarios**: healthcare, Industry 4.0, mobile services, military (UAV swarms), vehicles (IoV) — not central to this summary.
4. **Q4 — Trends/lessons/challenges**: fully-connected topology dominates current practice (~50% of surveyed papers) despite its O(N²) cost; no DFL-native aggregation algorithm has emerged as a de facto standard the way FedAvg has for CFL; scalability, trust, and use of RL for optimizing DFL are flagged as open/critical challenges (the paper explicitly lists "Explore the use of Reinforcement Learning" as a future direction — RL applied *to* DFL, not the reverse, but a useful citable hook).

## The key concept: how DFL answers "how do you decentralize the aggregation step"

The paper's decentralization-approaches figure (Section III-A-3) formalizes the spectrum precisely as a 5-step training lifecycle (local train → exchange → aggregate → exchange → update):
- **CFL**: steps 1–2 done locally, but a single central server does step 3 (aggregation) alone — single point of failure, bottleneck, trust dependency.
- **SDFL**: an aggregator *role* rotates among participants (chosen randomly or by capability); aggregation is still done by one node per round, but which node changes over time — a hybrid.
- **DFL**: every node independently does all four steps — local train, send params to neighbors, **aggregate locally** (each node runs its own aggregation over what its neighbors sent it), send again. There is no elected/rotating aggregator at all — aggregation is fully local and topology-dependent.

Concretely, the aggregation step itself is decentralized via **consensus-style algorithms operating over the network graph rather than a star**: Decentralized SGD (DSGD), Decentralized FedAvg with Momentum (DFedAvgM), Dynamic Average Consensus-based FL (DACFL), FedPGA (partial-gradient exchange), and gossip-averaging variants (CHOCO-SGD, S-FedAvg used in GossipFL). Each of these replaces "send params to server, server averages, broadcast back" with "average with whatever neighbors you're connected to, repeated until the whole graph reaches approximate consensus on the global model" — this is literally distributed averaging/consensus optimization (à la Nedić et al.'s foundational DSGD, 2009) applied to model parameters instead of a scalar.

## Connection to your thesis (Decentralized/Federated Multi-Agent RL)

**Why centralized FL is a bottleneck for multi-agent RL.** The paper's own motivation for DFL maps directly onto your thesis's core critique of CTDE-style centralization: a single aggregating server (i) is a single point of failure — if it goes down, the whole federation stalls, exactly as a crashed central critic would halt CTDE training; (ii) is a bottleneck, since all N clients must communicate with one node each round (communication cost `M·N`, Table in Sec. III-D), which for a multi-agent RL setting scales badly as agent count grows — this is your "more agents → worse training / curse of dimensionality" concern from a communications-infrastructure angle, not just a joint-action-space angle; and (iii) creates a trust dependency — one entity controls what the "global" policy/value function becomes, which is a poor fit for autonomous agents (vehicles, robots) that may not share a trust domain in a real deployment.

**Topologies that remove the central server.** The paper gives you a concrete menu, each with different implications for a decentralized MARL system:
- **Fully connected**: most robust/fault-tolerant (survives node loss) but O(N²) communication — realistic only for small agent teams, not "scalable" MAS.
- **Gossip / P2P over partial topologies** (ring, random/Erdős–Rényi, or ad hoc neighbor discovery): each agent only talks to a handful of neighbors, communication cost grows linearly rather than quadratically, and the mechanism is inherently asynchronous — a good match for agents that move, drop in/out, or have only local sensing range (this is precisely the DTDE/local-communication setting from the MARL-AD survey, `summary_marl_ad_survey.md`, and matches Qu et al. 2020's networked-agent actor-critic that exploits "exponential decay of influence over network distance").
- **Node clustering / hierarchical**: aggregation happens within similarity- or proximity-based clusters first, then across clusters via proxy nodes — a natural fit if your agents naturally partition into sub-teams (e.g., squads, regions) and you want two-level aggregation instead of flat gossip.

**Best candidate analogue for a fully decentralized MARL setting: gossip-based DFL over a partially-connected (ring/random) topology, using a consensus-style aggregation algorithm (DSGD/DFedAvgM/DACFL), implemented via a framework like Fedstellar.** Reasoning:
- Fedstellar is the strongest framework candidate because it is topology-agnostic by design (fully connected, star, ring, random — configurable), supports all three decentralization schemas (CFL/DFL/SDFL) in one platform so you can run controlled comparisons, works in both simulated and real physical/virtual deployments, and already reports DFL matching or beating CFL on convergence time (32% faster than CFL in one reported MNIST experiment) — i.e., it's built exactly for the "vary the topology, keep the model/task fixed" experiments your thesis needs.
- Gossip communication is the best-matched communication mechanism (over pure P2P or fully-connected) because it tolerates the dynamic, intermittent connectivity that real multi-agent systems (vehicles, drones, mobile robots) actually have — matching the paper's own point that gossip is asynchronous and works over "close neighboring nodes," which is the natural communication graph for spatially distributed RL agents.

**Combining with CTDE.** CTDE's central critic is, functionally, a CFL aggregator: during training it collects joint observation/action information from all agents (analogous to a server collecting model updates) and produces a single value estimate used to compute policy gradients, which is then "broadcast" back to each agent's actor update. To decentralize this without losing CTDE's benefit (agents get information beyond their own local view during training), replace the central critic's aggregation step with a **DFL-style consensus/gossip aggregation of local critics**: each agent maintains its own local critic, periodically exchanges critic parameters (or gradients) with its topology neighbors using DSGD/DFedAvgM/DACFL-style averaging, and after enough gossip rounds each agent's critic converges toward an approximation of what a fully centralized critic would have learned — all without any node ever seeing the full joint state or acting as a permanent aggregator. Execution stays fully decentralized (agents act on local critics/policies, as CTDE already prescribes), but now *training* is decentralized too, giving a genuinely serverless "federated CTDE": approximately-centralized training information via periodic neighbor consensus, decentralized execution, and no single point of failure — directly answering the gap the MARL-AD survey (`summary_marl_ad_survey.md`) flagged: CTDE's "unconstrained, instantaneous" communication assumption is unrealistic, and this paper's DFL aggregation mechanisms are the concrete recipe for relaxing it.

## Suggested next reads
1. Nedić et al., *"Distributed Subgradient Methods for Multi-Agent Optimization"* (2009) — the DSGD algorithm underlying most DFL consensus aggregation; foundational for understanding convergence guarantees over arbitrary graphs.
2. Chen et al., *"DACFL: Dynamic Average Consensus-Based Federated Learning"* (2022) — closest to a principled "gossip toward global consensus" algorithm with convergence proofs for convex objectives; worth checking whether the convexity assumption is a blocker for RL value/policy networks.
3. Fedstellar paper (Martínez Beltrán et al., 2023) and its GitHub repo — evaluate as the experimental platform for running federated/decentralized MARL experiments across topologies.
